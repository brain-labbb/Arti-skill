# Nano3D 实验结果表

本文件按 [`Nano3d.md`](/mnt/zsn/lyb/arti-skill/exp/Nano3d.md) 的 12 张表回填。本地已运行 **33 个既有导出资产的 existing-export pilot**，并保留 **2026-08-05 冻结的 33 个既有模板 × 固定 seeds 0–35 = 1,188 seed 的 seed-distribution Reliability 历史快照**；其 33/33 template hashes 均已与 current HEAD 漂移，不代表当前代码得分。该快照测量模板在 seed 分布上的编译/QC 质量，但仍不是 54 个任务的模板生成与 repair benchmark。基于同一批 1,188 个最终 package，另完成 source-derived Constraints v1 审计。`N/A` 表示缺少 Nano3D 规定的 gold/spec、编辑任务、物理 sweep 或成本遥测，不能由现有资产直接推出；带 `*` 的数值是 source-derived、结构审计或既有模板 proxy，不是论文 hidden-spec 复现或新模板生成成功率。

下方以 `paper` 标记的行是对应原论文报告值，不是本地重新运行结果；不同方法按各自论文的 item set 报告，不能直接当作同一批输入的本地复现。`N/R`（not reported under the exact Nano3D protocol）表示该方法是有效主对照，但论文没有报告这一列的同定义结果，必须在冻结共同任务上重跑，不能用相近指标代填。

**指标含义。** `Parts` 是每个资产的可渲染部件节点数，只反映结构粒度，并非越多越好；本地 existing-export 与论文行使用 GLB mesh nodes，对照组直接评测使用 URDF renderable-visual links，具体单位必须随行读取。`Named / Nameability` 是名称未命中冻结占位规则的词法比例；它不自动证明名称可读或语义正确，opaque 命名需另行披露。`Semantic Precision` 是输出名称中有多少真正描述了该部件，防止“每个节点都乱取一个详细名字”；`Semantic Recall` 是 gold 要求的语义部件中有多少被找到；`Functional Richness` 按预先设计定义为“正确命名的 spec functional roles / required functional roles”，不奖励额外装饰件或更细的 link 切分；extra-real parts 单独报告。`Instance Discriminability` 检查同类多实例能否区分，例如 `left_door` 与 `right_door`；`Cross-Seed Consistency` 检查同一模板不同 seeds 对相同角色是否采用稳定命名或稳定角色计数；`Over-Segmentation Rate` 是一个真实语义部件被无意义拆成多个节点的比例。除 Parts 需结合类别复杂度解释外，Precision、Recall、Functional Richness、Discriminability、Consistency 越高越好，Over-Segmentation 越低越好。

**指标含义。** `mesh component` 是一个资产内被独立读取的三角网格对象，一个资产可以包含多个 mesh components；因此 `N=54 assets` 与 `547 mesh components` 是两种不同分母。`Watertight` 检查每个 mesh component 是否形成无孔洞闭合表面，本地行先算每资产的 component 通过比例再取 macro mean，并同时给出 component-level 分子/分母。`Manifold` 是 edge-manifold proxy：每条无向边最多邻接两个面，允许边界，不检查 vertex-manifold，所以不能把它理解成“完全闭合且拓扑无误”。`Open Edges` 是只邻接一个面的边数，越少越好；`Degenerate Faces` 是零面积、重复点或病态三角面数，越少越好，但两者都会受三角化密度影响。`Self-Intersection` 是互不相邻面片发生穿插的数量或比例，越少越好。`Source KB`、`URDF KB`、`Mesh KB` 分别是生成源代码、结构描述和几何文件大小，只衡量存储/可维护成本，不直接代表质量。`Portable Package` 是把被评分的完整最终 package 及其声明依赖复制到干净环境后，所有相对路径和依赖仍可解析。`Deterministic Build` 要求相同代码、配置和 seed 做至少两次 fresh build 后得到相同规范化 artifact/hash。`Semantic Complete` 要求输出无关 spec 规定的必需部件、名称和角色齐全；name/tree field proxy 不能替代它。`Kinematic Complete` 是关节 parent/child/type/axis/origin/limit 等必需字段同时通过。`Physical Complete` 是原生 package 的 collision、positive mass/inertia、joint damping/friction 和 contact/friction metadata 同时通过；运行时临时默认值不算。`N/E` 表示指标适用但本轮未按严格协议执行，`N/A` 表示该表示或证据层不适用。

**指标含义。** `Template Runs` 是创建或调用 generator 的次数，需区分一次性 authoring 与已有 generator 的 marginal seed 生成；`Agent Turns` 是模型观察反馈并继续修改的轮数；`Compile/Probe Count` 是实际执行代码、编译资产或调用验证器的总次数；`Wall Time` 是用户等待的真实时间，应同时报告总时间和每任务均值/中位数；`Input Tokens` 与 `Output Tokens` 分别是发给模型和模型生成的 token；`Total Tokens` 是两者之和；`API Cost` 是按当时模型价格折算的调用费用；`Source LOC` 是最终可执行源代码行数；`Source Size` 是最终源程序或不可编辑输出文件大小。Turns、probes、时间、tokens 和成本在相同成功标准下越低越好；LOC/size 主要衡量可维护性和存储开销，不是视觉或物理质量。PV-A 还应分别报告一次性模板构建成本与每个 seed 的边际成本，不能只展示较小的边际时间。
